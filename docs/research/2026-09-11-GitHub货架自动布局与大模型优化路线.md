## 3. 推荐的自动布局算法结构

### 3.1 先确定不可改变的输入

固定门店多边形和孔洞、障碍/禁放区、已知门洞、可用墙段、工作点、模板以及业务需求。通道宽度来自输入规则；现有样例的 1,200 mm 是测试参数，本调研不把它解释为适用于所有门店的法规值。

CAD 来源或规划范围缺失时应保持需补充输入的状态；模型可以提出待确认的问题和候选，不能填造边界、门洞或确认状态。

### 3.2 搜索通道、货架排和组合

推荐以“货架排/背靠背组合”为搜索单位，避免一开始独立搜索每块货架的浮点坐标。一个提案描述允许的方向、深度、通道模式、排列顺序及局部重排动作；受控解码器生成实际模块、占地、取货面和 BOM。

可以分两步扩展：

1. **现有候选空间内的搜索。** 复用当前方向、深度、通道模式、单双面与余量分支，比较均匀搜索、人工优先级、模型优先级在相同预算内的效果。
2. **增加真实布局邻域。** 由程序实现整组移除/重建、合法排段重选、局部平移、排端对齐及背靠背/单面替换。每步重新生成关联的组合、取货面和数量信息，再完整验证。

第一阶段重点是更快获得合法解；第二阶段才可能发现当前枚举集合之外的更好布局。

### 3.3 用 ALNS 做局部重排

建议先实现少量有明确含义的算子：

- 选择补货绕行较长的局部区域，移除其中少量完整组合，再优先保留连接通道重建。
- 选择尾部剩余或碎排较多的区域，重新切分合法排段并调用现有模块动态规划。
- 保留门洞和主连接通道，对中央排与沿墙排的顺序重新组织。
- 在模板和配对规则允许的情况下比较单面与背靠背结构。

这些是待开发的领域算子，ALNS 库不会自动提供。该库默认以单个 `objective()` 驱动接受规则；若用于六目标布局，可对冻结尺度下的目标组合做多次搜索，同时维护独立 Pareto 档案，不能直接把指标字典传入就声称实现多目标优化。

### 3.4 用 CP-SAT 解决局部组合难点

优先考虑有限候选排段或模块位置，而非一次求解整店所有坐标。先由几何引擎生成完整占地合法的候选，计算互斥关系，再由布尔选择变量决定选哪些排段；已有候选位置是否互斥必须计入完整组合、通道与排端约束。

如直接求坐标，使用明确的整数单位和允许方向；非矩形区域需要额外约束，不能用外接矩形替代。单纯不重叠不证明通道连通；首轮可固定经验证的通道，再对局部货架选择求解，返回后复算完整路线。

CP-SAT 只对实际编码的模型给出状态。`FEASIBLE` 不等于最优，超时 `UNKNOWN` 不等于无解；即使得到 `OPTIMAL`，也只是该离散模型及目标内最优。[官方状态说明](https://developers.google.com/optimization/cp/cp_solver)

### 3.5 路线策略与布局策略分开做对照

当前路线政策是加权“最近未访问目标，再到目的点”，见[operations_routes.py:24](C:/D/汉斯/secondunderstand/services/planning/operations_routes.py:24)。可以借鉴 GABAK，对少量任务点使用精确访问顺序，或对较大任务增加局部改良，但这属于另一个实验变量。

先固定路径政策比较新旧布局，再固定布局比较新旧路径政策。否则可能把路线求解变好误报成货架布局变好。

## 4. 大模型如何让算法持续优化

ReEvo 的方法是让大模型根据不同启发式的优劣反思，再生成新策略；EoH 则同时演化策略描述与实现代码。论文研究支持这种方法在组合优化中的可行性，但不能据此声称其在本项目上已有效。[ReEvo 论文](https://arxiv.org/abs/2402.01145)、[EoH 论文](https://arxiv.org/abs/2401.02051)

建议采用离线循环：

```mermaid
flowchart LR
    A[现有算法与训练场景] --> B[大模型提出小范围策略改动]
    B --> C[受控运行策略并生成布局]
    C --> D[独立复算几何 可达性 BOM]
    D --> E[固定指标与预算比较]
    E --> F[保留优良且不同的策略]
    E --> G[整理失败案例与指标差异]
    G --> B
    F --> H[封存验证集与人工审阅]
    H --> I[固定版本供设计服务使用]
```

大模型适合优化：候选评估优先级、选择哪个区域重排、选择哪个移除/重建算子、何时跳出局部最优，以及后续受控启发式函数的实现。纯数值参数调优应同时保留随机搜索等低成本对照，检验模型是否带来额外价值。

模型可根据实际证据给出类似“某类凹形门店的补货任务绕行较长，优先重建该区域”的下一轮建议；说明中的失败原因要能对应具体测试 ID、几何或路线证据，不能只接受模型自述的改善。

### 首个可演化接口

建议先限制为如下形态，名称仅为待实现接口：

```python
def rank_candidate_specs(scene_features, specs):
    """返回现有候选规格的优先顺序；不生成坐标、不改变约束。"""

def choose_repair_action(layout_features, allowed_actions, history):
    """返回一个允许的局部重排动作 ID，由可信代码执行。"""
```

只有构建并验证了重排算子，第二个函数才有扩大搜索空间的价值。随后可以对单个启发式实现做代码进化，逐步扩大修改范围。

### 评价器必须独立

模型不得修改门店输入、业务需求下限、指标公式、验证器、冻结基线、测试答案和验收状态。大模型所在的协调进程可以访问按量 API Key；候选代码运行环境不应继承密钥，也不应获得生产目录写权限。优先传递明确 JSON 动作；执行生成代码时需要独立受限运行环境、时间/内存上限和外部结果复算。

这不是现成进化框架自动保证的属性。例如本次 EoH 的 [BaseProblem 实现](https://github.com/FeiLiu36/EoH/blob/472545785c936dcfc863d2bc0d6109cf23c7ce62/eoh/src/eoh/problem.py#L92)会执行生成代码，不能把函数签名或子进程超时当成完整权限隔离；[FunSearch 官方仓库](https://github.com/google-deepmind/funsearch)也明确没有附带执行不可信代码的沙箱。

模型在离线实验中改进算法；通过验证后，将选定代码固定为普通规划服务版本。日常出图可不依赖在线模型调用。记录代码、提示词、模型标识、输入/评估器哈希、随机种子、各轮输出、调用量和时间；LLM 输出并不因设置随机种子就一定可完全复现，因此需要保存实际生成内容。

## 5. 如何证明是改进，而不是分数变好看

### 硬条件和质量分开

最终接受的方案必须满足：完整占地在有效范围内、无越界/碰撞、门口和保留区不被占用、净宽及排端条件成立、全部取货面和任务路径有效、模板/组合/BOM 一致、固定业务下限满足。允许搜索中产生被拒绝的候选，但最终结果不可用高容量分数抵消硬约束失败。

同时保留：有效取货面、名义层板面积、拣货平均/较差路程、补货平均/较差路程，以及碎排、尾余、模块数、时间和失败率。真实商品容量缺少数据时仍记为 `UNKNOWN`。

### 必须修正跨实验比较口径

当前 [operations.py:208](C:/D/汉斯/secondunderstand/services/planning/operations.py:208)从每次候选前沿提取各指标理想值。不同搜索算法产生不同候选集，因此不能直接比较两次运行各自的 `worst_normalized_regret`，把它当作统一收益。

实验评分应固定训练阶段确定的归一化尺度和参考点，或在事先约定的统一候选集合上重算对照；封存验证时不能按新算法的结果重新挑选有利尺度。保留原始六项指标及可行率，以相同业务需求比较，展示路线和容量间的取舍。

### 建议的对照组

| 组别 | 用途 |
|---|---|
| 当前完整 M11 | 冻结质量与可行率基线 |
| 相同候选集合的随机/均匀顺序 | 检验 LLM 候选排序是否胜过简单策略 |
| 人工编写 ALNS 算子与选择规则 | 检验增加局部搜索本身的收益 |
| 相同算子集合的 LLM 选择策略 | 分离大模型策略的额外收益 |
| 后续 LLM 改写局部启发式 | 在允许的接口和算子版本内比较代码进化收益 |

候选集合、路线政策、模板、需求、硬件和评估预算按组别目的固定。既比较相同精确评价次数下的质量，也比较相同墙钟时间下的结果；记录实际调用量与超时，不以尝试次数代替时间成本。

### 数据拆分和试验停止

现有场景适合作为可见回归起点；曾用于选择算法的场景不能再宣称是未见测试。建议新增程序化扰动的训练集，另分开发验证集和一次性封存验证集，覆盖凹形、窄区、柱网、不同门位、不同允许方向、模板及任务负载。最终封存集的具体案例与逐例反馈不进入模型提示。

模型调优允许查看训练集失败证据；验证集只用于有限次数的版本选择，最终测试保留到最后。算法在本来可行的病例上的解决率不得低于冻结基线；预期不可行/输入不足的病例单独评价正确拒绝，不能为了“100% 成功”放松条件。

建议首轮先评估一个小接口、少量候选程序和明确的总时间/调用上限，按实测每场景耗时再扩展。没有稳定收益、达到预算或连续多轮没有有效新方案时停止并保留基线；不承诺自动无限改进。

## 6. 与当前代码接入时的两个约束

1. 当前发布入口 [_seal](C:/D/汉斯/secondunderstand/services/planning/operations.py:83)会重新匹配 `corridor_plans()` 的合法通道候选。任意新通道拓扑不能直接进入正式结果。初期在现有通道契约内搜索；后期增加新拓扑时，明确版本化的通道提案和独立验证规则。
2. 当前[生成机制检查](C:/D/汉斯/secondunderstand/services/planning/operations_layouts.py:519)限制主轴、深度、组合及生成字段；移动或替换货架后，关联实例、组合、取货面、邻接关系、余量和 BOM 必须由可信解码器重建。不能只改坐标或删除来源字段绕过校验。

几何和业务不变量保持独立；新增表示方式时可以人工审阅并扩展验证器契约，但不得让进化程序同时修改规则和自己的评分。已有路线缓存采用完整模块/组合/取货面身份；新缓存还要绑定完整输入、模板、规则和路线策略版本，不能对坐标粗略取整后复用。

## 7. 建议的实施顺序与交付物

| 阶段 | 工作与可交付结果 | 进入下一阶段的依据 |
|---|---|---|
| 第一阶段：实验入口 | 固定 M11 基线、单候选评价函数、训练/验证隔离、统一指标、限时运行、JSON 差异报告 | 原有回归通过；同一输入/代码可重放；评价器不受候选程序修改 |
| 第二阶段：局部重排 | 小规模人工 ALNS 算子；必要时比较 CP-SAT 局部修复；保留已知合法解 | 在同等预算下量化收益，明确最差病例和容量/路线取舍 |
| 第三阶段：模型进化 | 选 EoH 或 ReEvo 思路实现一次闭环；模型改策略、程序执行和评分、自动保留较优版本 | 超过随机/人工策略对照并通过封存验证，而非只超过训练分数 |
| 第四阶段：门店应用 | 接入经确认的真实 CAD/业务输入，评审候选，固定算法版本用于设计页 | 技术验证和真实门店人工验收分别通过 |

最值得首先实现的不是整套大模型平台，而是“单候选评价入口 + 少量可验证的局部重排动作”。这会同时服务 ALNS、CP-SAT、人工算法和后续大模型实验，且能检验大模型究竟增加了什么价值。
